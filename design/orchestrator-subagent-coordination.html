1

Problem and goal

When the orchestrator runs a fleet of subagents, work is lost and trust breaks in the interactions between them.

Five documented ways, from three weeks of real usage — 3,235 messages across 85 sessions: fleets launched into broken environments that die hours later; finished work destroyed because silence was misread as death; agent claims believed without proof; evidence destroyed by our own cleanup; unaccounted sessions writing to the repo while the orchestrator blamed ghosts.

Goal. Every orchestrator–subagent interaction — starting, communicating, believing, stopping, accounting — governed by checks that hold even when the orchestrator's judgment doesn't. The recurring failure is not ignorance of the rules; it is a model drifting past rules it knows. So the design target is: guarantees that survive a bad day.

Non-goals. No cross-session supervisor or auto-retry. No escalation detectors. No auto-selected rigor. No protection against non-agent externalities (API overloads, network, MCP health). And no attempt to make subagents answer on a deadline — §2.2 shows that is impossible rather than merely hard.

2

Constraints — platform facts and what can be known

Two kinds of constraint bound this design: facts about the platform, measured directly; and what those facts imply about which knowledge is even reachable. Both are constraints — the second kind just takes analysis to see.

2.1Platform facts

Measured on Claude Code CLI 2.1.220, with version skew as the standing re-check. First, three terms this document uses precisely:

  • Subagent — a separate, complete Claude session that the orchestrator launches to do one job. No shared memory with the orchestrator, no heartbeat between them.
  • Working log (the platform calls it a transcript) — a file the platform itself writes to disk for every session, including every subagent, recording everything that session does, continuously, as a built-in behavior. This design adds nothing to make it exist. It is the agent's activity record — distinct from any document the agent was asked to produce.
  • Exchange — one round between the user and the orchestrator: the user sends a message, the orchestrator works (possibly launching a dozen subagents over half an hour), and control returns to the user. The platform stamps every tool call inside one exchange with a single shared identifier.
#FactWhat it forces
P1The platform's only enforcement primitive is intercepting a tool call before it runs: a deterministic script with seconds of budget, no model, and no access to the conversation, delivering a verdict by exit code. Subagent starts and stops are both interceptable this way.Enforcement can exist — but only at these two chokepoints, and only over what a fast script can read.
P2Nothing fires when an agent dies or is stopped. Natural completion emits an event; a stop emits nothing.Death cannot be watched for. Guarantees must sit on the orchestrator's own actions, not on observing agents.
P3A subagent reads messages only between its own actions. While it is inside a tool call — running a test suite, doing a long search — it cannot see or answer anything.Response deadlines are unenforceable by construction. Silence must carry zero evidential weight.
P4The exchange identifier covers everything in one user round — measured spanning 29+ minutes and a dozen subagents. There is no finer-grained shared clock between orchestrator and subagents."It happened in this exchange" says nothing about "it happened recently." Any freshness rule keyed to the exchange never expires in exactly the sessions that matter.
P5When the orchestrator asks the platform to stop a subagent, the request contains only the text the orchestrator typed — the name it gave the agent — not the agent's internal identity. The platform does not translate between them. Separately, every agent in a fleet shares the orchestrator's session identifier.Any gate on stopping must translate name → identity itself. One environment check can cover a whole fleet — but actors within a fleet are indistinguishable by their keys alone (until wave 3 adds identity).
P6Every subagent's working log and a small metadata record (its name, type, model) are on disk, readable by scripts, updated as the agent works.The one continuously-updated, machine-readable trace of real activity — the foundation of §2.2.
P7Stops initiated by the human — the UI button, terminating the process — bypass the tool pipeline.The human's own actions stay outside every wall, honestly.

2.2Derived constraints — what can be known about a subagent

From P1–P7, everything the orchestrator can ever learn about a subagent arrives through five channels — and they are not equally trustworthy. The split below is the design's first commitment: evidence may ground an action; a signal may only prompt evidence-gathering. Nothing in the signal tier is ever a legitimate basis for starting, stopping, or believing anything.

Why this split is right — the distinguishing property is causal: the evidence tier consists of artifacts produced by the work itself (a byproduct log, a contracted output, the agent's own words), while signals are the platform's scheduling bookkeeping about the work. Bookkeeping about attention was measured wrong in both directions in live operation; byproducts of work cannot be wrong about whether work happened. Two refinements keep the split honest: the task registry's terminal states (completed, stopped) are authoritative and count as evidence — it is only "running" that proves nothing; and an agent's message splits in two — its arrival is evidence of life at send-time, while its content is only as good as the proof attached, which is what the reporting contract (§3.3) exists to fix.

Evidence — may ground action

Working log

Written continuously as a side effect of working — the agent cannot work without producing it, which is what makes it unfakeable. Its last-write time is the agent's last real activity: a write 41 seconds ago means alive, definitively. It also contains the agent's actual output — including work finished but never delivered.

that a quiet log means death — a ten-minute tool call writes nothing until it returns.

Contracted deliverable

The output file the agent was told, at launch, to produce. Present and substantive = the job is done, whatever else is true. Its meaning comes from the contract: we named it, so its existence answers exactly the question we care about.

failure, from absence — the agent may be seconds from writing it. And it proves nothing at all if no deliverable was contracted at launch — which is what makes the work contract (§3.3) load-bearing.

Message from the agent

Alive at the moment of sending, plus its content — the only channel carrying the agent's own account.

anything from its absence (P3); and its content is only as trustworthy as the proof attached.

Signals — may only prompt a look at the evidence

Task registry, while "running"

The runtime still schedules the task. (Its terminal states — completed, stopped — are authoritative and are evidence.)

the difference between working and hung — the only distinction that matters while running.

Idle notification

The platform observed a pause.

completion, delivery, or death. Measured this session: idle arrived before delivery four times, after delivery five times, once mid-delivery.

The asymmetry that governs everything

A response proves alive; silence proves nothing (P3). Any rule built on silence is built on nothing. Every rule in this design is therefore built on the evidence tier only — and where evidence would be missing at decision time, the design's job is to have created it in advance.

What remains unknowable

Two things no channel answers: whether a silent agent is thinking or hung (the working log goes quiet in both cases), and the moment of death (P2). The design treats the first with a bounded procedure (§3.4) and the second by never depending on death detection at all.

3

Architecture — derived

Given the failure mode (§1) and the constraints (§2), the shape below is close to forced. This section walks the derivation, then introduces each piece at the moment it becomes inevitable — a reader who can re-derive the architecture can also tell when a future change breaks it.

3.1The derivation

GIVEN

The failure mode is the orchestrator's own judgment lapsing mid-drift (§1). So the guarantee cannot live in the orchestrator's context — instructions there are exactly what a drifting model ignores. It must live outside the model.

AND

The only external enforcement point the platform offers is tool-call interception (P1): a fast deterministic script, no model, no conversation, at exactly the moments that matter — the start and the stop.

BUT

Such a script cannot gather evidence. It cannot probe an environment, read a fleet's working logs, or weigh a deliverable inside its seconds-long, conversation-blind window. It can only check facts already written down.

SO

Evidence must be gathered before the guarded moment — by the orchestrator, the only actor that can — and written into machine-readable state where the gate can read it. Evidence-gathering and enforcement are necessarily different actors at different times, and state is the only possible interface between them.

AND

Whatever cannot be expressed as a fact-check at a chokepoint — how to compose a launch, when to message a quiet agent, what a substantive deliverable looks like — cannot be walled at all. It lands in procedure: pinned text, enforced by review and audit, honest about being the weakest layer.

The design theorem

A wall can only enforce what was written down before the moment it must decide. Every guarantee in this system is therefore a pair: an act of evidence-gathering that writes state, and a gate that refuses the guarded action when that state is missing, foreign, or stale.

3.2The three layers

Interception — the gates

The chokepoints P1 provides. A gate reads state and the active plan, never the conversation; its entire vocabulary is allow silently or refuse loudly, naming the exact command that fixes it. Gates are installed machine-wide and must therefore be inert anywhere no wave is running.

State — the written-down evidence

Small, per-repo, ephemeral files, each written by exactly one producer and read by exactly one gate. Ephemerality is deliberate: this is operational evidence with a natural lifetime, and the durable record is the copy mirrored into the plan. The layer boundary rule that follows from the derivation: producers may think; gates may only read. The moment a gate needs judgment, the design is wrong — that judgment belonged upstream, in a producer, writing its conclusion down.

Procedure — everything unwallable

The composition of launches, the handling of quiet agents, the standards of belief — everything requiring judgment at a moment with no chokepoint. Pinned by span tests so the text cannot drift silently, policed by review and audit rather than machinery, and honestly the weakest layer: the walls exist precisely to backstop its failures at the two irreversible moments.

3.3The entities

The derivation forces a small set of things to exist. Each is here for one of two reasons: it makes an evidence channel usable, or it writes evidence down in advance so a gate can read it later. Nothing else earns an entity.

3.4How the entities are used — the four interactions

The goal names the interactions: starting, communicating and believing, stopping, accounting. Each is one composition of the entities above; the two irreversible ones get walls.

Starting — walled (wave 1)

An agent may be started when three things hold: the environment is proven working this session (a fleet inherits its environment and dies collectively — the attestation reifies the check); a work contract exists (the start is where the stop's future evidence gets created — an agent launched without a contracted deliverable is undecidable by construction); and the launch is ledgered at the moment it happens, not reconstructed later.

Communicating and believing — procedure now, contract in wave 2

Outbound, the work contract tells the agent what to produce and where; inbound, the reporting contract makes claims self-verifying. No tool chokepoint exists for believing, so this interaction can never be walled — its enforcement is the audit chain, which is why the contracts must be written artifacts rather than habits.

Stopping — walled (wave 1)

An agent may be stopped when: its deliverable exists and is substantive (finished — take the work, no timing judgment needed); or nothing new has appeared in its working log since a recorded observation, no deliverable exists, and the non-response procedure's round has run. Never on an idle notification, never on elapsed silence, never without an observation newer than the agent's last activity — three prohibitions that are all the signal-tier ban applied.

Accounting — wave 3

Every launch writes a roster row; every quiet agent resolves through the non-response procedure to a recorded outcome; unexpected repo changes are checked against the roster and surfaced instead of built upon. This interaction acquires its own state (the roster) and may acquire gates later; wave 1 ships only the warn-only detection of other live sessions.

4

Components

Four components realize the two walled interactions. Described by contract — what each may assume, must produce, and must never do. File names are the realization, listed last.

The environment check — producer, start

Contract: verify what a fleet dies without — credential present, repo writable, state directory writable — and record context that informs judgment without blocking (git baseline; a warn-only scan for other live sessions). Write the attestation keyed to this session, atomically; on failure write nothing and destroy any earlier attestation. May take seconds and think; runs once per session. Never: write an unkeyed attestation; leave a stale pass standing. Named limit: proves the credential is present, not valid — expiry detection needs a live API call (backlog).

The start gate — gate, start

Contract: on every subagent start, machine-wide: if a wave is active and no attestation from this session exists — refuse, naming the exact fix command. Otherwise pass in silence. It parses no check detail: the attestation's existence is the verdict, by the producer's contract. Never: print on the allow path (an allowing gate that talks is a nagging gate); block where no wave is active.

The observation — producer, stop

Contract: given a target by name or identity, resolve it against on-disk metadata (P5) and print that agent's evidence tier: working-log recency as absolute time and age, its last message, repo activity, and each contracted deliverable's existence and substance. Decide nothing. Its run is observed by machinery, which records the target and the activity level seen — making "an examination happened" a fact rather than a memory. Never: stop anything, judge anything.

The stop gate — gate, stop

Contract: on every stop request during an active wave: resolve the typed name (P5), find an observation of that target from this session, check freshness (D-1). Any failure — no record, foreign session, unresolvable or ambiguous name, staleness — refuses, naming the observation command. Never: pass on ambiguity once a wave is active (a stop is irreversible; the ambiguous case is the wall's purpose); wall a machine with no wave running.

Realization

environment check → hooks/preflight-probe.sh · start gate → hooks/dispatch-preflight.sh · observation → hooks/stop-check.sh · stop gate → hooks/stop-guard.sh (one script, two registrations: it records observations and gates stops) · state → .bionic/tmp/{preflight,stop-check}.state

One realization note: the two producers live in the hooks/ directory for test-harness pairing but are not hooks — the component boundary is the registration list, not the folder.

5

Decisions — ratified 2026-08-04

All six decisions were ratified together on 2026-08-04 and are now binding design. Each block preserves the first-principles argument that carried it.

D-1When is an observation still fresh?
The question

The stop gate needs a rule for how long a recorded observation remains valid grounds for a stop.

From first principles

An observation is a snapshot of the evidence tier. It stops being true the moment the evidence changes — and the working log says precisely when that is: the agent's next write. Any other rule is a proxy for this one, and every proxy fails somewhere: clock windows are arbitrary numbers that expire honest observations of dormant agents and admit stale ones inside the window; keying on the exchange identifier was adopted and then disproven by P4 — one exchange spans a 29-minute fleet, so the observation never expires exactly where fleets are largest.

The rule

A stop is permitted only if the target's last activity is no later than what the observation recorded. Agent did something since you looked → observation stale, by definition. Agent dormant since you looked → observation valid, however old. Checked against UC-5: the founding incident is refused; the 23-minute dormant case passes honestly.

Recommended: adopt, as wave 1's corrective slice before merge. No clocks; completes the doctrine — session boundary for environments, activity boundary for stops.

D-2Does one observation permit one stop, or many?
From first principles

An observation is evidence about one target at one moment. Letting the record ride for repeated stops re-admits staleness through the side door D-1 just closed. Consuming it on use makes the invariant airtight: every stop individually evidenced.

Recommended: adopt with D-1 — cheap, and together they are the complete guarantee.

D-3Whose observation counts?
The gap

P5: every actor in a fleet shares one session key, so today a subagent running the observation quietly lowers the wall for the orchestrator's later stop of that target. The observer's identity isn't in the record because per-actor identity doesn't exist yet — it is precisely wave 3's roster.

Recommended: route to wave 3; carry the interim exposure as a named limitation. (D-1 shrinks it: a borrowed observation also goes stale on the target's next write.)

D-4Does the wave carve survive this document?
From the architecture

The carve now has a derivation instead of an intuition: wave 1 = the two walled interactions (start, stop) as producer→state→gate pairs; wave 2 = the believing interaction's contracts (work contract made checkable, reporting contract — audit-enforced, since no chokepoint exists for belief); wave 3 = the accounting interaction's state (roster), which also closes D-3 and D-5. Each wave is one coherent increment; none depends on a later one.

Recommended: keep the three waves; wave 1 absorbs the D-1/D-2 corrective slice before merging.

D-5Concurrent sessions sharing one repo
The gap

State files are one-slot-per-repo while validity is per-session — two live sessions overwrite each other's attestation (observed during this epic's own verification, which needed a restore step). Fail-closed, so safe; mutually annoying. Per-session filenames are the fix, and are identity work.

Recommended: route to wave 3 with the roster; until then a collision costs one re-run of a three-second check.

D-6How long do we wait? — time, contracts, and long-running work
The question

A test-runner executes an hour-long regression suite. Its working log is silent the whole time — one long tool call produces its result once, at the end — so "no activity for 47 minutes" describes both a healthy suite and a wedged one. How long does the orchestrator wait before acting, and is that bound anything better than discretion?

From first principles

Two wrong answers first. A global kill-timer violates the founding asymmetry — elapsed time is not evidence of anything, and a timer stops work for being slow, destroying the legitimate suite at minute 59. Pure discretion is the opposite failure: unbounded waiting with no defined trigger. Both errors come from trying to read time as evidence. Time is a signal.

The resolution has two parts. First, evidence has a level below the agent. The working log is the byproduct of work at the agent level, and a long tool call silences it — but the task itself has byproducts: the suite writes output continuously. We cannot make the platform update the working log on a schedule, but we can contract the agent to run long commands so their output accrues at a named path. The observation then checks one more thing — the progress artifact's age — and "working log quiet 47 minutes, progress file grew 12 seconds ago" is alive, definitively. The ambiguity dissolves for exactly the long-running case.

Second, expected duration becomes a contract field. The orchestrator knows at launch what it is dispatching — a regression suite is an hour, a file search is minutes. So the expectation is declared per task, by the party holding the knowledge, at the moment it exists — not by a global constant. And exceeding it is a signal, never evidence: going overdue does not justify a stop; it triggers the non-response procedure mechanically. The eventual stop still requires the fresh observation (D-1). Discretion shrinks to reading evidence; the trigger stops being discretionary at all.

The bound

Total wait ≤ declared duration + the procedure's two rounds. Every action inside it is evidenced; the healthy long-runner is never at risk.

Recommended: adopt — two work-contract fields (expected duration; progress-artifact path for long tasks), the observation's progress-artifact check, and overdue-as-trigger semantics. The contract fields belong to wave 2 (the contract wave); the practice is adoptable immediately as procedure in every long-running brief.

6

Use cases, end to end

The design against its actual workload. Three of the six were observed live during this epic's own construction — marked as such, with the real outcomes.

UC-1Normal fleet launch

Orchestrator opens a wave. Runs the environment check — five results print, attestation written. Each subagent start passes the gate silently (attestation present, session matches). Each launch carries a work contract and writes a ledger row; work proceeds.

Design cost — one command and ~3 seconds per session; the gate adds milliseconds per start.

UC-2Launch into a broken environment

Same, but the credential is missing. The check fails, writes no attestation, deletes any old one. The first start is refused with the fix command in the message. The failure surfaces at minute zero, loudly — instead of hours later as dead agents and lost work, which is the §1 incident this pair exists for.

Channels used — none needed: the evidence was created before any agent existed.

UC-3Quiet read-only agent holding finished workobserved live

A review agent goes idle without delivering. Idle is a signal, so it grounds nothing. The observation runs: working log written 41 seconds ago, last message "I already completed this review — resending now." Verdict from evidence: alive and finishing. The orchestrator recovers the review from the working log instead of stopping the agent.

As observed — the stop gate forced exactly this observation after the orchestrator, acting on the idle signal, had already requested the stop. The wall caught its own operator; the recovered review contained the wave's most important finding.

UC-4Quiet writing agent, work complete but uncommittedobserved live

An implementor idles without committing or reporting. Writers are never messaged back to life — a resumed second instance collides with the first on the same files. Evidence instead: the repo shows its edits present and correct; the diff is read; the orchestrator commits the work itself and stands the agent down with one final message.

Procedure outcome — taken over. Bounded; no destruction, no waiting forever.

UC-5Stop attempted on stale informationobserved live · the founding incident

An agent is examined; it looks unpromising. Minutes later — after it has committed its work — a stop is requested on the strength of that earlier examination. Under D-1 the gate compares the observation's recorded activity level against the working log now: the agent wrote after the observation, so it is stale by definition and the stop is refused until the orchestrator looks again — at evidence that now includes the commit.

Contrast — the pre-epic version of this event destroyed finished work; the v1 design (exchange-keyed freshness) provably re-permitted it. The activity boundary is the fix — exactly what D-1 asks you to ratify.

UC-6A second session on the same repo

The environment check's scan finds another live session's working log and warns with its identity — as it did, correctly, on its first real run. Warn-only in wave 1: the orchestrator and user decide. Wave 3's roster upgrades this from "someone else is here" to "these specific changes are not ours," making foreign work a defined event instead of a mystery.

Boundary — detection, never prevention: two humans may absolutely run two sessions; the design's job is that neither is ever confused about it.

UC-7The hour-long test suite

A test-runner is launched with a contract declaring: run the regression suite, expected ~60–75 minutes, output accruing to a named progress file, verdict file as the deliverable. Minute 30: an idle notification arrives — a signal, grounds nothing, correctly ignored. Minute 47: the orchestrator gets nervous and runs the observation: working log quiet for 47 minutes — but the progress file grew 12 seconds ago. Alive, busy. No judgment call was needed. Minute 80: now overdue — the non-response procedure triggers mechanically. The observation this time shows the progress file also stopped growing 25 minutes ago and no deliverable exists. One follow-up message (test-runners are read-only), nothing arrives; a re-observation shows no change at any level. The stop proceeds — fresh observation in hand per D-1 — and is reported.

What time did — elapsed time appeared exactly once, as the trigger for the procedure. Every action was grounded in evidence; the healthy suite was never at risk; the wedged one was caught within one declared-duration plus two bounded rounds.

Failure model

One principle generates the table: the default direction follows the cost asymmetry of the guarded action. A missed start-wall costs one unchecked launch; a false start-wall nags every session on the machine — so starts fail open. A missed stop-wall destroys unrecoverable work; a false stop-wall costs one diagnostic re-run — so stops fail closed. Where no wave is active there is no decision to guard, so everything passes.

Security

Threat model: an untrusted repo — which controls its own plan files, .bionic/ contents, and ignore rules — meeting these gates installed machine-wide.

The load-bearing property: a hostile repo can close or aim the walls but never open them — opening requires the victim's own session keys, which the repo cannot learn. Closing (a planted plan file arms the walls in that repo) costs one refused action — annoying, disclosed, not destructive.

Fixed during this epic's review: predictable temporary filenames plus symlink-following redirects allowed an arbitrary file overwrite — proven with a working exploit, closed with unpredictable names, regression-tested by planting a symlink and proving nothing writes through it.

Accepted and named: refusal messages print a plan path into model context (a hostile repo can choose a filename that reads as an instruction — bounded, no execution); the docs-root setting can aim plan discovery and disclose filename existence; the observation prints a slice of a subagent's working log, which is its purpose — the reader is the defense. The prior credential-leak class (command text reaching logs) is verified not reintroduced.

9

Verification strategy

Organized around the lesson this epic paid for: wave 1's test fixtures were single-exchange while its claims were about long, multi-agent exchanges — and that gap is exactly where the design flaw survived an audit. Hence:

  • Every wall is a verification instrument, so its tests must prove it catches — planted violations go red against the pre-wall state — and passes the positive pair, since a wall that refuses everything is equally broken.
  • Mutation-and-restore is the durable proof: remove the guard, watch named checks fail, restore byte-identical, watch them pass. Red counts die at green; this survives integration.
  • Deliberately duplicated logic (a shared library was rejected — a sourced file the installer misses is a silently inert wall) carries behavioral agreement tests driving every copy.
  • The installed layer is verified live: fresh sessions after a real install, refusal and permission both observed semantically.
  • Binding on waves 2–3: at least one verification scenario per wave must be long-exchange, multi-agent, against installed binaries — the configuration the epic exists for and v1 never tested.
10

Rollout and operations

  • Bootstrap installs the scripts and registers the two gates. The user runs bootstrap — always, never an agent.
  • Gate registration takes effect for new sessions; a live session keeps its start-time configuration. Verifying installed behavior therefore means fresh sessions, and upgrading means: bootstrap, then next session.
  • A rename leaves the old file behind in the installed directory until the manifest-driven cleanup runs — verify on the next bootstrap (open item from this epic's own rename).
  • State is per-repo and ephemeral, wiped at wave close; anything evidence cites is mirrored into the plan first. Uninstall runs through reset and the same manifest.
  • Standing gap outside this epic: path-scoped rule files do not distribute to other machines at all.
